# 결정 장부

핵심 규칙이나 구조를 바꾸면 여기에 번호·날짜·결정·근거를 추가한다.

**쓰는 법**

- 번호(`D-001`)는 다시 쓰지 않는다. 틀린 결정도 지우지 말고, 뒤집는 새 항목에서
  `D-005 를 뒤집는다` 라고 밝힌다 — **뒤집힌 이력 자체가 근거**다
- **결정보다 근거가 중요하다.** 무엇을 정했는지는 코드를 보면 알지만,
  왜 그 대안을 버렸는지는 여기에만 남는다
- 커밋 메시지에서 `(D-00x)` 로 참조한다

### D-001 · 2026-08-17 · 코드는 처음부터 반응형 한 파일, 배포만 맥으로 시작

**문제**: "맥용을 먼저 만들고 나중에 안드로이드용으로 확장" 하는 게 나은지 검토했다.

**결정**: 코드는 처음부터 반응형 단일 파일로 만들고, **배포 방식만** 맥 로컬 파일에서
시작한다. 안드로이드로 넓힐 때 같은 파일을 그대로 올린다.

**왜 다른 방법을 안 골랐나**: 단일 HTML 에는 "맥용 코드"와 "안드로이드용 코드"가 따로
없다. 실제 차이는 ①여는 방법(로컬 파일 vs URL) ②화면·입력(마우스 vs 터치) 둘뿐인데,
①은 코드가 아니라 배포의 문제라 나중에 정해도 다시 만들 게 없고, ②는 이 앱이 원래
"한 항목만 크게" 구조라 큰 글씨·큰 버튼이 그대로 모바일 레이아웃이 된다. 즉 지금
넣는 비용이 거의 0이다. 반대로 맥 전용으로 만들었다가 나중에 손대면 레이아웃·터치
영역·폰트 크기를 전부 다시 만지게 된다.

**한계**: 실제 안드로이드 기기에서 확인하기 전까지 모바일 동작은 ⚠️미검증이다.
반응형으로 짰다는 것과 실기기에서 쓸 만하다는 것은 다르다.

### D-002 · 2026-08-17 · 의존성 0의 단일 HTML 파일

**문제**: 여러 기기에서 실행할 것이라면 설치·빌드·서버가 필요 없어야 한다.

**결정**: `index.html` 파일 하나에 HTML·CSS·JS·소리를 전부 넣는다.
프레임워크·빌드 도구·CDN·웹폰트·외부 이미지·오디오 파일 없음.

**왜 다른 방법을 안 골랐나**: 루틴 목록을 별도 `routines.json` 으로 빼는 쪽이 구조는
깔끔하지만, `file://` 로 열면 `fetch` 가 CORS 로 막혀 **로컬 실행 자체가 불가능**해진다.
서버를 띄우는 순간 "더블클릭하면 켜진다"는 이 앱의 유일한 장점이 사라진다.

**한계**: 파일 하나가 길어진다. 섹션 주석으로 구분해 견딘다.

### D-003 · 2026-08-17 · 소리는 WebAudio 합성, 그리고 소리는 보조 신호다

**문제**: 완료 시 "띵" 소리가 필요하다. 그런데 소리는 기기 사정으로 안 날 수 있다.

**결정**: 오디오 파일 없이 WebAudio 로 짧은 종소리를 합성한다. 지원 기기에서는 짧은
진동을 곁들인다. 그리고 **소리가 안 나도 앱이 온전히 쓸 수 있도록**, 완료의 주 신호는
화면 전환(사라지는 애니메이션 + 진행 표시)으로 둔다.

**왜 다른 방법을 안 골랐나**: mp3 를 base64 로 박으면 파일이 무거워지고, 별도 파일로
두면 D-002 를 깬다. "소리를 주 신호로" 두지 않은 이유는 실패 경로가 너무 많기 때문이다
— 무음 모드, 볼륨 0, 브라우저 자동재생 정책, iOS 의 벨소리 스위치(WebAudio 도 막힌다),
iOS Safari 의 진동 미지원. 이 중 어느 하나만 걸려도 소리에 의존한 앱은 못 쓰게 된다.

**한계**: 합성음이라 음색을 세밀하게 고르기 어렵다. 실기기에서 들어보고 조정한다.

### D-004 · 2026-08-17 · 늘어나는 타이머, 시각 차이로 계산

**문제**: 항목마다 실제 소요시간을 재고 싶다. 남은 시간을 재촉하는 카운트다운은 원하지 않는다.

**결정**: 항목이 뜨면 0부터 올라가는 스톱워치를 돌린다. 시간이 지정된 항목은 그 시간에
도달하면 알림만 울리고, **넘기는 것은 언제나 사용자의 완료 조작**이다.

계산은 `setInterval` 누적이 아니라 **시작 시각을 찍어두고 `Date.now()` 와의 차이**로 한다.

**왜 다른 방법을 안 골랐나**: `setInterval` 로 1초씩 더하는 방식은 탭이 백그라운드로
가면 브라우저가 타이머를 조여서 실제보다 적게 센다. 화면을 끄고 스트레칭을 하는 게
이 앱의 정상적인 사용 방식이므로, 그 상황에서 틀리는 계산법은 쓸 수 없다.

**한계**: 기기가 절전/최대 절전에 들어갔던 시간도 그대로 포함된다. 자리를 비웠다
돌아오면 시간이 크게 튄다 — 이건 정확한 값이지만 사용자가 원한 값은 아닐 수 있다.

### D-005 · 2026-08-17 · 기록을 남기지 않는다

**문제**: 완료 기록·연속일수·달성률을 남길지.

**결정**: 남기지 않는다. 세션이 끝나면 요약 화면에서 소요시간을 한 번 보여주고 버린다.

**왜 다른 방법을 안 골랐나**: 연속일수는 동기부여 장치이지만, 끊긴 날 앱을 열기 싫게
만드는 부작용이 있다. 그리고 localStorage 기록은 기기마다 따로 쌓여서(D-007) 어차피
신뢰할 수 있는 통계가 되지 못한다. 반쪽짜리 기록을 남기느니 안 남기는 쪽이 정직하다.

**한계**: 나중에 기록이 필요해지면 저장 구조를 새로 넣어야 한다. 그때 이 결정을 뒤집는다.

### D-006 · 2026-08-17 · 기본 목록은 파일에, 편집분은 localStorage 에

**문제**: 루틴 항목을 어디에 두고 어떻게 고칠 것인가.

**결정**: `ROUTINES` 상수로 기본 목록을 파일에 넣고, 화면에서 편집하면 localStorage 에
덮어쓴 목록을 저장한다. **기본값으로 되돌리기** 버튼을 반드시 둔다.

**왜 다른 방법을 안 골랐나**: 파일 편집만 가능하게 하면 폰에서 항목 하나 고치는 것이
불가능해진다. 반대로 localStorage 만 쓰면 새 기기에서 열었을 때 빈 화면이 뜬다.
둘을 겹쳐 두면 새 기기는 기본 목록으로 즉시 동작하고, 손보고 싶으면 그 자리에서 고친다.

**한계**: "지금 보이는 게 파일의 기본값인가 내가 편집한 것인가"가 헷갈릴 수 있다.
편집 화면에 현재 어느 쪽인지 표시한다.

### D-007 · 2026-08-17 · 편집한 루틴의 내보내기·불러오기를 넣는다

**문제**: localStorage 는 출처(origin)마다 따로 논다. `file://` 에서 편집한 루틴은
나중에 URL 방식으로 옮기면 사라지고, 맥에서 편집한 것이 폰에 가지 않는다.

**결정**: 편집 화면에 루틴 목록을 JSON 텍스트로 **내보내기 / 불러오기** 하는 기능을 둔다.

**왜 다른 방법을 안 골랐나**: 서버·클라우드 동기화는 D-002(단일 파일)를 깨고 계정·키
관리를 끌고 들어온다. 1인 사용자가 가끔 옮기는 용도에 그 비용은 과하다. 텍스트 복사·
붙여넣기는 몇 줄이면 되고 어디서나 동작한다.

**한계**: 수동이다. 옮기는 것을 잊으면 두 기기의 목록이 갈라진다.

### D-008 · 2026-08-17 · 진행 상태를 저장하지 않는다

**문제**: 루틴 도중 새로고침하거나 창을 닫으면 이어서 할 것인가.

**결정**: 저장하지 않는다. 다시 열면 처음부터다.

**왜 다른 방법을 안 골랐나**: 이어하기를 넣으면 "하루가 언제 바뀌는가"(자정? 새벽 4시?),
"어제 하다 만 것을 오늘 이어줄 것인가"를 전부 정해야 하는데, 기록을 안 남기기로 한
마당에(D-005) 중간 상태만 붙잡고 있는 건 앞뒤가 맞지 않는다. 루틴은 10~20분짜리라
처음부터 다시 하는 비용도 작다.

**한계**: 실수로 새로고침하면 진행이 날아간다. 실제로 자주 겪으면 뒤집는다.

### D-009 · 2026-08-17 · 형식은 HTML — 검토한 대안과 탈락 이유

**문제**: 단일 파일로 간다는 것(D-002)과 별개로, **애초에 왜 HTML 이라는 형식인가**.
네이티브 앱, 크로스플랫폼 프레임워크, 단축어, 기성 앱 등을 검토했다.

**결정**: HTML 로 만든다. 알림 예약 요구가 없으므로(아래) 재검토 조건도 사라졌다.

**왜 다른 방법을 안 골랐나**: "맥·태블릿·안드로이드에서 실행"이 형식을 결정한다.

| 대안 | 탈락 이유 |
|---|---|
| 네이티브 (Swift / Kotlin) | 맥과 안드로이드가 다른 언어·다른 프로젝트. 같은 앱을 두 번 만든다. 안드로이드 설치에 서명·사이드로드 또는 스토어 등록 필요 |
| Flutter / React Native | 양쪽 배포는 되지만 SDK·빌드 툴체인·에뮬레이터·의존성 관리가 따라온다. 항목 10개짜리 앱에 과하다 |
| Electron / Tauri | 데스크톱 전용. 모바일 요구사항을 못 푼다 |
| 터미널 스크립트 | 맥에서는 20줄이면 되지만 안드로이드에서 안 돈다 |
| Apple 단축어 | 맥·아이패드에서는 훌륭하나 **안드로이드에 없다** |
| Obsidian 플러그인 | 데스크톱 중심이고, 전용 UI 를 만드는 비용이 결국 HTML 과 같아진다. 루틴 실행이 노트 앱에 얹힐 이유도 없다 |
| 기성 앱 (Routinery 등) | 요구 기능을 이미 제공한다. 대신 구성이 그 앱 방식에 갇히고, 구독료가 붙고, 루틴 내용이 남의 서버로 간다 |

HTML 은 **런타임이 이미 모든 기기에 깔려 있는 유일한 형식**이다. 설치·스토어·빌드·서명이
전부 없고, 이 앱이 필요로 하는 것(큰 글자·버튼 하나·스톱워치·짧은 소리)은 브라우저
기본 기능으로 부족하기는커녕 남는다.

**PWA 는 대안이 아니다** — 같은 HTML 에 manifest·service worker 를 얹은 것이다.
나중에 URL 배포로 갈 때 더하면 되고, 지금 만드는 것을 버리지 않는다 (B-14).

**한계**: 브라우저라서 못 하는 것이 셋 있다 — ①정해진 시각에 먼저 알려주기
②다른 앱을 보는 동안 확실히 울리는 소리 ③잠금화면 위젯 등 시스템 통합.

이 중 ①이 이 결정을 뒤집을 유일한 조건이었으나, **"루틴은 내가 실행할 때 실행한다.
정해진 시간이 필요 없다"** 로 확인됐다(2026-08-17). 즉 이 앱은 **사용자가 열면 시작**하는
것이 설계이지 한계가 아니다. 나중에 예약 알림을 원하게 되면 이 항목을 뒤집는 것부터
시작한다.

### D-010 · 2026-08-17 · 이브닝 순서 — 번호는 지키고 무번호 15개는 임의 배치

**문제**: 받은 목록이 Todoist 의 "Sorted Alphabetically" 화면이라 **실행 순서가 아니다.**
이브닝 28개 중 번호가 있는 13개는 번호순으로 앞에 몰려 있고, 나머지 **15개는 번호가
없어 순서 정보가 아예 없다.** 게다가 번호도 겹친다 — `040` 이 Shower 와 페이스힐링,
`050` 이 거울과 코세척.

**결정**: **번호가 있는 항목은 번호 순서를 그대로 지키고**(겹치는 번호는 원본 화면에
나온 순서 유지), **번호 없는 15개만 임의로 배치**했다. 배치 근거는 모닝 루틴의 흐름
(정리 → 위생 → 피부 → 영양 → 수련 → 마무리)을 그대로 옮긴 것이다.
코드에서 `// [번호]` 와 `// [배치]` 주석으로 어느 쪽인지 항목마다 표시했다.

**왜 다른 방법을 안 골랐나**: 순서를 물어보고 기다리면 아무것도 못 만든다. 반대로
전부 내가 재배열하면 사용자가 실제로 지켜온 순서(번호로 남아 있는 의도)를 지운다.
**남아 있는 의도는 보존하고, 정보가 없는 곳만 채우는 것**이 되돌리기 가장 쉽다.

**한계**: 배치한 15개는 ⚠️미검증이다. 특히 `Turn off electronics` 는 맨 뒤에 뒀는데,
앞쪽에 두면 `시각화 동영상을 시청한다` 와 어긋나기 때문이다. 확인이 필요하다 (B-16).

### D-011 · 2026-08-17 · 항목 이름은 원문 그대로, 번호 접두사만 뗀다

**문제**: 원본 항목명이 `030. 허리운동 10회를 행한다` 처럼 번호 접두사를 달고 있고,
`Reflenesh`(→Replenish), `Aciton`(→Action) 같은 오타가 있다.
모닝의 `000. Morning Routine` 은 실행 단계가 아니라 머리글로 보인다.

**결정**: **번호 접두사는 뗀다**(배열 순서가 곧 순서라 화면에서는 노이즈다).
**`000. Morning Routine` 은 항목에서 뺐다.**
**오타를 포함한 나머지 문구는 원문 그대로** 둔다.

**왜 다른 방법을 안 골랐나**: 오타를 조용히 고치면 Todoist 원본과 문구가 달라져
나중에 대조할 때 같은 항목인지 헷갈린다. 남의 데이터를 말없이 고치지 않는다.
고칠지는 사용자가 정한다 (B-17).

**한계**: 큰 글씨로 뜨는 화면이라 오타가 눈에 잘 띈다.

### D-012 · 2026-08-17 · 병렬 항목 문제를 인지하되 지금은 풀지 않는다

**문제**: 목록에 **"시작해 놓고 다른 걸 하는" 항목**이 섞여 있다.
`오일풀링`(10~15분 물고 있는 동안 제자리뛰기·양치를 한다 — 원본 번호 061→062→070 이
정확히 그 순서다), `얼굴에 마스크팩을 한다`, `가습기를 켠다` 가 그렇다.

### D-014 · 2026-08-17 · GitHub Pages 배포 — 파일 자체가 동기화 채널이다

**문제**: "모든 기기의 루틴이 같아야 한다"는 요구가 뒤늦게 붙었다. Dropbox 에 올려
각 기기에서 여는 방식도 검토했다.

**결정**: **GitHub Pages 무료 플랜(공개 저장소)** 에 올린다. 앱을 저장소 루트의
`index.html` 로 두고, 매니페스트·서비스워커·아이콘을 함께 배포해 홈 화면 아이콘과
오프라인 실행을 붙인다. 루틴 내용은 `index.html` 안에 그대로 들어간다.

**왜 다른 방법을 안 골랐나**:

- **Dropbox 는 HTML 을 렌더링하지 않는다** (2017년 웹 호스팅 종료). 공유 링크는 다운로드만
  제공하고, 안드로이드에서는 "다운로드 → 파일 관리자 → 다른 앱으로 열기" 를 매일 반복하게
  된다. **홈 화면 아이콘을 만들 수 없고**, `file://` 에서는 localStorage 도 신뢰할 수 없다
- **안드로이드에는 맥 같은 로컬 동기화 폴더가 없다.** Dropbox 안드로이드 앱은 스트리밍
  기반이고 오프라인 파일은 앱 전용 캐시에 들어가 크롬이 접근하지 못한다. FolderSync 류로
  실제 경로에 내려도 `file://` 페이지는 **홈 화면 추가가 막혀 있다**
- **비공개 배포(Cloudflare Access, GitHub Pro)는 필요 없다** — "프라이버시는 상관없는
  내용" 으로 확인됐다. 인증 단계를 없애는 쪽이 매일 쓰는 앱에 낫다
- **기기별 붙여넣기(빈 껍데기 배포)는 동기화와 정반대**라 요구가 바뀌면서 탈락했다

**핵심**: 정적 호스팅에서는 **파일 자체가 동기화 수단**이다. `push` 한 번이면 다음에
열 때 전 기기가 같은 루틴을 본다. 별도 동기화 장치가 필요 없다.

**한계 — 되돌아오는 경로가 없다**: 정적 호스팅에는 받아 적을 서버가 없으므로 **앱 안에서
편집한 것은 그 기기 localStorage 에만 남는다.** 전 기기에 반영하려면 원본을 고치고 push
해야 한다(맥에서, 또는 폰 브라우저로 github.com 에서 직접). 편집 화면의 역할은
**"이 기기에서 시험해보고 텍스트를 만들어내는 것"** 으로 재정의된다.
매일 편집하게 되면 루틴을 별도 텍스트로 빼서 앱이 읽어오게 하는 것을 검토한다 (B-20).

**서비스워커는 네트워크 우선**으로 짰다. 캐시 우선이면 push 한 수정이 며칠씩 안 내려가
"전 기기가 같다"는 이 결정의 목적 자체가 깨진다.

### D-015 · 2026-08-17 · 앱은 루틴을 저장하지 않는다 — D-006·D-013 의 저장 부분을 뒤집는다

**문제**: D-014 로 GitHub Pages 배포를 정하고 나니 구멍이 드러났다. **앱 안에서 편집해
저장한 기기는 자기 사본을 들고 있게 되어, push 한 수정을 영영 못 받는다.** 게다가
`기본값으로 되돌리기` 를 지운 뒤라 그 상태를 푸는 방법이 앱 안에 없었다.

**결정**: **루틴을 localStorage 에 저장하지 않는다.** `index.html` 의 `ROUTINES` 가
어느 기기에서나 유일한 원본이다. 편집 화면은 남기되 **저장 대신 `전체 복사`** 를 둔다 —
고쳐서 복사해 가는 곳이지, 이 기기에 남기는 곳이 아니다. localStorage 에는 소리 설정만.

**왜 다른 방법을 안 골랐나**: 사용자가 **"편집은 맥북으로만, 안드로이드는 편집하지
않는다"** 로 범위를 좁혀줬다(2026-08-17). 그러면 기기별 사본을 허용할 이유가 사라진다.

- `동기화본으로 되돌리기` 버튼을 되살리는 안 — 갈라진 뒤에 되돌리는 장치다. 애초에
  갈라지지 않게 하는 쪽이 낫다. 버튼 하나 + 상태 표시 + "지금 보는 게 어느 쪽인가"라는
  혼란이 전부 사라진다
- 편집 화면 자체를 없애는 안 — 텍스트를 눈으로 보고 줄을 옮겨보는 값이 크다. 특히 줄
  번호가 붙은 뒤로는 순서를 짜기 좋다

**얻은 것**: "어느 기기가 최신인가"라는 질문이 성립하지 않게 됐다. 전 기기가 항상
같은 파일을 본다. 코드도 줄었다 (`loadRoutines`·`isCustom`·`saveRoutines` 삭제).

**한계**: 맥에서 고친 것을 반영하려면 반드시 원본을 고치고 push 해야 한다 — 앱만으로는
완결되지 않는다. 오프라인에서는 반영할 수 없다.

### D-016 · 2026-08-17 · 맥앱은 URL 을 띄우는 네이티브 껍데기로

**문제**: 맥에서 독 아이콘으로 실행할 앱이 필요하다. 세 가지 방법이 있었다.

**결정**: **WKWebView 네이티브 앱**(`mac/Routine.swift`, ~110줄 → `mac/routine.app`)을 만들어 배포 URL 을
띄운다. 네트워크가 안 될 때만 앱에 동봉한 `index.html` 사본으로 넘어간다.

**왜 다른 방법을 안 골랐나**:

| 대안 | 탈락 이유 |
|---|---|
| Safari `Dock에 추가` | 코드 0줄로 되지만 Safari 에 묶이고, 창 동작·아이콘을 손댈 수 없다 |
| Chrome `--app=URL` 래퍼 | Chrome 이 깔려 있어야 하고, Chrome 업데이트/프로필 상태에 끌려다닌다 |
| HTML 을 앱 안에 넣기 | **이게 제일 위험하다.** 맥만 다른 버전을 보게 되고, 앱을 다시 빌드하기 전까지 push 한 수정이 맥에 영영 안 온다 — D-014·D-015 로 없앤 문제가 그대로 되살아난다 |

**핵심**: 원본은 언제나 URL 이다. 동봉 사본은 **오프라인 전용 비상구**이고, 평소에는
쓰이지 않는다. `reloadRevalidatingCacheData` 로 항상 새것을 먼저 확인한다.

**빌드**: `tools/build-mac-app.sh` — swiftc 로 컴파일하고 `icon-512.png` 를 `sips`+
`iconutil` 로 `.icns` 로 바꿔 번들을 만든다. Xcode 본체 없이 Command Line Tools 만으로 된다.
의존성 0 원칙(D-002)이 맥앱에도 그대로 적용된다.

**한계**: 서명하지 않았다. 이 맥에서 빌드했으므로 격리 속성이 없어 그냥 실행되지만,
**다른 맥으로 복사하면 Gatekeeper 가 막는다** (우클릭 → 열기로 통과 가능).
그리고 `index.html` 이 바뀌면 동봉 사본은 낡는다 — 다시 빌드해야 갱신된다.
평소에는 URL 을 보므로 문제되지 않지만, **오프라인 사본은 마지막 빌드 시점**이다.

### D-017 · 2026-08-17 · 앱이 스스로 갱신을 확인한다

**문제**: 안드로이드에 push 한 수정(편집 버튼 감추기, 이름 `Routine`)이 며칠이 아니라
**영영 도달하지 않는 상태**였다. 서버에는 새 파일이 올라가 있는 것을 `curl` 로 확인했는데
기기만 옛 화면을 보고 있었다. 원인은 둘이 겹친 것이다.

1. **GitHub Pages 가 `cache-control: max-age=600` 을 보낸다.** 서비스워커가 네트워크
   우선으로 `fetch(request)` 를 해도 브라우저 HTTP 캐시가 10분간 낡은 응답을 돌려준다
2. **홈 화면에 설치한 PWA 에는 주소창도 새로고침 버튼도 없다.** 앱 전환기에서 다시
   열어도 기존 페이지가 이어질 뿐 새 내비게이션이 일어나지 않는다. 즉 **기기가 서버에
   갈 일 자체가 없었다**

**결정**: 두 곳을 다 막는다.

- 서비스워커가 `cache: 'reload'` 로 요청해 **브라우저 HTTP 캐시를 건너뛴다**
- 앱이 켜질 때와 **다시 보일 때마다 `registration.update()`** 로 새 워커를 확인하고,
  새 워커가 제어권을 잡으면 `location.reload()` 로 한 번 새로고침한다

**안전장치 둘**: 첫 설치 때는 새로고침하지 않는다(제어권이 처음 생기는 것뿐이다).
**루틴 진행 중에는 새로고침하지 않는다** — 진행 상태를 저장하지 않으므로(D-008) 새로고침이
진행을 지운다.

**왜 다른 방법을 안 골랐나**: 매번 전부 새로 받는 것이 낭비로 보이지만 파일이 40KB
남짓이고, **"전 기기가 같은 루틴을 본다"(D-014)가 트래픽 절약보다 압도적으로 중요하다.**
캐시 우선 전략은 애초에 이 목적과 양립하지 않는다.

**한계**: 이미 옛 버전을 물고 있는 기기는 이 코드가 없으므로 **한 번은 손으로 풀어야
한다** — 설치 삭제 후 재설치, 또는 크롬에서 사이트 데이터 삭제. 이번 한 번뿐이다.

### D-018 · 2026-08-17 · `전체 복사`는 클로드코드용 지시문까지 함께 만든다

**문제**: 편집 화면에서 텍스트를 복사해도, 붙여넣은 뒤에 "이걸 어디에 어떻게 반영해라"를
매번 사람이 다시 써야 했다. 반영 경로가 사람의 기억에 의존한다.

**결정**: `전체 복사`가 **본문 + 지시문**을 함께 클립보드에 넣는다. 붙여넣기만 하면
반영과 배포까지 이어진다. 지시문에는 대상 경로, 교체할 상수(`ROUTINES.morning` /
`.evening`), 형식 설명, 그리고 **항목 개수**가 들어간다.

**개수를 넣는 이유**: 붙여넣다 줄이 잘려도 알아챌 방법이 그것뿐이다. 루틴이 28개인데
27개가 도착하면 반영 전에 걸린다 — **사람도 나도 눈으로는 못 세는 숫자**다.

**왜 다른 방법을 안 골랐나**: 지시문 없이 본문만 복사하고 매번 말로 설명하는 쪽은,
설명이 조금씩 달라지면서 엉뚱한 곳에 반영될 여지를 남긴다. 반대로 앱이 GitHub 에 직접
쓰게 만드는 쪽은 토큰이 필요해 공개 페이지에서는 불가능하다 (D-014 한계).

**부수 개선**: 클립보드 실패 경로를 `execCommand` 폴백으로 보강했다. 그래야 `file://`
에서 연 맥앱 오프라인 폴백 화면에서도 복사가 된다.

**한계**: 지시문에 프로젝트 경로가 하드코딩된다. 폴더를 옮기면 지시문도 고쳐야 한다.

### D-019 · 2026-08-17 · 맥 아이콘은 웹용과 따로 만든다

**문제**: 맥앱 아이콘이 독·파인더에서 다른 앱들보다 **눈에 띄게 커 보였다.**

**결정**: 아이콘을 두 종류로 나눈다. `tools/make-icons.py` 가 둘 다 만든다.

| 용도 | 파일 | 모양 |
|---|---|---|
| 웹·안드로이드 | `icon-192.png`, `icon-512.png` | 캔버스를 꽉 채움 |
| 맥 | `mac/icon-mac-1024.png` | 1024 안에 824 둥근 사각형 + 투명 여백 |

**왜 다른가**: **PWA 는 OS 가 아이콘을 마스크로 잘라내므로 꽉 채워야 하고**(여백을 주면
두 번 줄어든다), **macOS 는 준 대로 그리므로 여백을 직접 넣어야 한다.** 애플 표준 비율은

쓰면 어느 한쪽은 반드시 어긋난다.

**한계**: 애플의 정확한 스퀘어클(연속 곡률) 대신 일반 둥근 사각형을 썼다.
나란히 놓고 재보면 모서리 곡률이 미세하게 다르지만 눈으로는 구분되지 않는다.

### D-020 · 2026-08-17 · 맥앱에서는 버튼 하나로 클로드코드까지 실행한다

**문제**: `전체 복사`(D-018)로 지시문까지 만들어도, 터미널을 열고 클로드코드를 띄우고
붙여넣는 세 동작이 남았다.

**결정**: 맥앱 안에서는 그 버튼이 **`클로드코드로 보내기`** 로 바뀌고, 누르면 터미널이
열리며 프로젝트 폴더에서 `claude` 가 지시문과 함께 실행된다. 브라우저·안드로이드에서는
기존대로 복사만 된다 — `window.webkit.messageHandlers` 유무로 갈린다.

**안전 설계 — 프롬프트를 셸 명령에 끼워 넣지 않는다**:
프롬프트를 임시 파일에 쓰고, 고정된 명령이 그 파일을 읽게 한다
(`claude "$(cat '<임시파일>')"`). 셸 명령에 들어가는 값은 우리가 만든 경로 두 개뿐이라
**프롬프트 내용이 무엇이든 명령을 벗어날 수 없다.** 더해서 메시지 핸들러는 현재 URL 이
우리 도메인이거나 동봉 사본일 때만 동작한다.

**왜 이 경계가 필요한가**: 이 앱은 **네트워크에서 받아온 페이지**를 띄운다. 그 페이지가
네이티브에 셸 명령을 시킬 수 있게 만들면, 페이지가 바뀌는 순간 임의 명령 실행이 된다.
그래서 네이티브 쪽은 "무엇을 실행할지"를 절대 페이지에서 받지 않는다.

**한계**: 프로젝트 경로가 앱에 하드코딩된다(`~/Projects/루틴 실행기 제작`). 폴더를
옮기면 앱을 다시 빌드해야 한다. 그리고 터미널 제어에는 macOS **자동화 권한**이 필요해
**첫 실행 때 한 번 허용**을 눌러야 한다.

### D-021 · 2026-08-17 · 맥앱 빌드 산출물은 `.noindex` 폴더에 둔다

**문제**: Alfred 에서 `routine` 을 치면 같은 앱이 **4개** 떴다. 디스크에는 빌드본
(`mac/routine.app`)과 설치본(`/Applications/routine.app`) 둘뿐인데, Alfred 의 파일
캐시(`filecache.alfdb`)가 **같은 파일을 경로 표기별로 따로** 담고 있었다. 네 가지가 겹쳤다:

| 원인 | 캐시에 든 경로 |
|---|---|
| 빌드본과 설치본이 둘 다 앱 | `mac/routine.app` · `/Applications/routine.app` |
| 대소문자 표기 차이 | `~/projects/…` (폴더명을 `Projects` 로 바로잡기 전의 낡은 항목) |
| firmlink 표기 | `/System/Volumes/Data/Applications/routine.app` |
| **한글 자모 정규화(NFC/NFD) 차이** | `루틴…` 이 `EBA3A8`(NFC) 과 `E18485 E185AE`(NFD) 두 벌로 |

캐시 테이블에는 경로 유일성 제약이 없고, 마지막 원인은 애초에 **바이트가 다르므로**
제약이 있었어도 걸러지지 않는다. 게다가 학습 기록(`knowledge.alfdb`) 6건이 하필
낡은 소문자 경로에 붙어 있어서 **그 항목이 1순위로 올라왔다.**

**결정**: 빌드 산출물을 **`mac/build.noindex/routine.app`** 에 만든다. 이름이 `.noindex`
로 끝나는 폴더는 **Spotlight 가 색인하지 않는다**(Xcode 의 `DerivedData/…​.noindex` 와
같은 방식). 그러면 앱으로 잡히는 것은 설치본 하나뿐이라 표기가 몇 벌이든 중복이 생기지
않는다. 낡은 캐시 4행과 학습 기록 6행은 한 번 지웠다.

**왜 캐시만 지우지 않았나**: 캐시를 지워도 다음 빌드에 빌드본이 그대로 다시 색인된다.
**중복은 캐시의 버그가 아니라 "앱 두 벌을 색인 가능한 곳에 둔" 구조의 결과**이므로
구조를 고쳐야 재발하지 않는다.

**한계**: `.noindex` 는 Spotlight 색인만 막는다. Finder 로 그 폴더에 들어가면 앱은
그대로 보이고 더블클릭으로 실행된다. 그리고 이미 다른 도구가 잡아 둔 낡은 항목까지
지워 주지는 않는다.

### D-023 · 2026-08-28 · 루틴을 여러 개로 — 빈도로 두 층을 나눈다

**문제**: 루틴이 모닝·이브닝 둘뿐이라는 전제가 코드 곳곳에 박혀 있었다.
`pickMode()` 는 토글 두 개를 갱신했고, 어두운 톤은 `body[data-mode="evening"]` 에
걸려 있었으며, 회귀 검사는 `["morning","evening"]` 을 손으로 적어 돌았다.
여기에 `수련과 운동` 과 `출국 전 체크리스트` 를 더하려면 전제부터 걷어내야 했다.

그리고 새 루틴들은 **쓰는 빈도가 서로 다르다.** 수련과 운동은 매일이지만 출국 전
체크리스트는 몇 달에 한 번이다. 넷을 한 줄로 늘어놓으면, 거의 안 쓰는 것이 매일 쓰는
것과 같은 크기로 매일 눈에 들어온다.

#### 결정 1 · 루틴 하나 = 키 하나, 메타를 데이터에 둔다

`ROUTINES` 의 각 항목에 `label` · `short` · `tier` · `theme` 을 붙이고,
화면·편집 탭·회귀 검사가 전부 `Object.keys(ROUTINES)` 를 읽게 했다.
**루틴을 늘릴 때 손댈 곳이 이 객체 하나**가 된다.

- **왜 데이터에 두나** — 대안은 화면마다 `if (mode === 'evening')` 을 두는 것이었다.
  그러면 루틴을 하나 늘릴 때마다 고칠 곳이 네댓 군데로 흩어지고, 그중 하나를
  빠뜨리면 "시작은 되는데 톤이 안 바뀌는" 식으로 **조용히** 어긋난다
- **`theme` 을 따로 둔 이유** — 어두운 톤은 원래 "이브닝이라서"가 아니라
  "잠들기 전 밝은 화면을 피하려고" 넣은 것이었다(SPEC). 그 근거는 루틴 이름이 아니라
  **그 루틴을 도는 시간대**에 있으므로, 이름에 매다는 대신 값으로 뺐다.
  그래서 CSS 선택자도 `[data-mode="evening"]` 에서 `[data-theme="dark"]` 로 옮겼다
- **`short` 를 따로 둔 이유** — `출국 전 체크리스트` 를 진행 중 표시나 편집 탭에
  그대로 넣으면 자리를 다 먹는다. 이름을 줄여 쓰는 곳이 두 군데 이상이라 값으로 뺐다

#### 결정 2 · 빈도로 두 층 — `main` 은 시작 화면, `more` 는 `☰` 뒤

`tier: 'main'` 은 시작 화면에 큰 버튼으로 바로 뜨고, `tier: 'more'` 는 오른쪽 위
`☰` 를 눌러야 나온다.

- **버린 대안 1 · 넷을 한 줄로** — 위에 적은 이유로 버렸다. 매일 쓰는 것을 고르는
  일이 가끔 쓰는 것 때문에 느려진다
- **버린 대안 2 · 최근 사용 순 자동 정렬** — 자리가 매번 바뀌면 **손이 위치를
  기억하지 못한다.** 매일 같은 시각에 같은 버튼을 누르는 앱에서 이건 손해다.
  순서는 `ROUTINES` 에 적은 순서로 고정한다
- **`☰` 안에서는 시간대 제안을 하지 않는다** — 가끔 쓰는 것에 "지금 시간" 을 붙일
  근거가 없다

#### 결정 3 · 고르기와 시작을 한 번의 조작으로

예전에는 `토글로 고르기` → `시작 누르기` 두 번이었다. 이제 루틴 버튼을 누르면
**바로 시작**한다.

- 고르기가 셋 이상이 되면서 토글이 감당하지 못하게 된 것이 계기지만, 두 번 누르던
  것이 한 번이 되는 건 그 자체로 이득이다. 잘못 눌러도 `홈`(D-022)이 있다
- **시간대 제안은 남긴다.** 다만 "선택해 둔 상태"가 아니라 **제안된 하나만 채워서**
  그린다 — 예전 `시작` 버튼이 있던 자리를 그것이 대신하는 셈이다
- **제안은 화면을 그릴 때마다 다시 계산한다.** 예전에는 페이지를 열 때 한 번만
  계산해 두었는데, 앱을 종일 띄워 두는 기기에서는 정오를 넘겨도 옛 제안이 남는다

#### 제1 원칙과 충돌하지 않는다

시작 화면과 `☰` 목록은 **루틴 이름**을 늘어놓는 곳이지 **항목**을 미리 보여주는
곳이 아니다. "다음에 할 것이 뭔지 미리 보이면 안 된다"는 원칙은 루틴 안쪽의 이야기다.

#### 회귀 검사도 함께 늘렸다 (79건 → 127건)

`["morning","evening"]` 고정을 `Object.keys(ROUTINES)` 로 바꿨다 — **루틴을 늘리면
검사도 저절로 늘어난다.** 여기에 메타 검사(5번)를 새로 넣었다: `label`·`short`·
`tier`·`theme`·`items` 가 갖춰졌는지, `main` 이 하나라도 있는지, 시간대 제안이
가리키는 `morning`·`evening` 키가 실재하는지.

**왜 메타 검사인가** — 루틴을 늘리다 `theme` 하나를 빠뜨리면 화면이 흰 채로 돌 뿐
아무 오류도 안 난다. 조용히 어긋나는 종류라 정적 검사가 값어치를 한다.
반대로 **버튼 크기·터치감·톤이 실제로 눈에 편한가는 여전히 못 잡는다** —
`CLAUDE.md` 1번 그대로다.

#### 한계 — 새 루틴 두 개의 항목은 자리표시자다

`수련과 운동` 7개와 `출국 전 체크리스트` 14개는 **내용을 받지 않은 채 넣은 자리표시자**다
(사용자가 "뼈대 먼저" 를 골랐다). 코드 주석과 `UPDATES.md` 에 표시해 두었고,
실제 목록을 받으면 `items` 를 통째로 교체한다 (B-27 · B-28).
**지금 상태로 수련 루틴을 돌면 남의 순서를 도는 것**이라는 점을 잊으면 안 된다.

#### 갱신 이력 문서를 따로 뒀다 (B-29)

`docs/UPDATES.md`. `STATUS.md` 는 늘 현재 시점 하나만 담아 **지난 상태를 덮어쓴다** —
그래서 "언제 무엇이 바뀌었나" 를 물을 곳이 `git log` 밖에 없었고, 그건
`CLAUDE.md` 9번이 하지 말라고 못박은 방법이다. 그 질문을 맡을 문서를 만든 것이다.
근거는 여전히 결정 장부에 남기고, 이력 문서는 **바뀐 것과 확인 상태**만 적는다.

### D-024 · 2026-08-28 · 뷰 방식은 루틴이 정한다 — "한 항목"은 순서가 중요한 루틴의 규칙이었다

**문제**: 루틴이 넷이 되고 나서(D-023) 성격이 다른 루틴이 섞였다.
`출국 전 체크리스트` 는 **순서와 무관하게 빠르게 훑고 체크하는** 목록인데,
한 번에 한 항목만 보여주면 열네 번을 눌러야 무엇이 남았는지 알 수 있다.
빠뜨린 것이 없는지 확인하는 것이 그 루틴의 목적인데, 화면이 그것을 막고 있었다.

**결정**: `ROUTINES.<키>.view` 로 루틴마다 뷰 방식을 정한다.
`'one'` 은 한 번에 한 항목, `'list'` 는 전체 목록이다.
모닝·이브닝·수련과 운동은 `'one'`, 출국 전 체크리스트는 `'list'` 다.
실행 중에는 항목 화면 오른쪽 위 버튼(`▤ 목록` / `▣ 하나씩`)으로 그 회차만 뒤집을 수 있다.

#### 제1 원칙을 뒤집은 것이 아니라, 어디에 걸리는 원칙인지 밝힌 것이다

`CLAUDE.md` 2번은 "다음 항목이 무엇인지 미리 보이면 안 된다"이고, 그 근거는
**전체가 눈에 들어오면 압박이 되고 어디까지 했는지 계속 다시 세게 된다**는 것이었다.
사용자의 말이 그 범위를 정확히 짚었다:

> morning routine과 evening routine처럼 실행순서가 매우 중요한 routine들은 한 번에
> 하나의 액션만이 보이는 것이 유효하다. 그렇지만 출국 전 체크리스트와 같이 여러
> 목록을 한 번에 보면서 순서와 무관하게 체킹을 빠르게 해야 하는 루틴도 있을 수가
> 있다. 그러한 루틴들은 "리스트형 보기"가 더욱 유효해보인다.

즉 그 근거는 **실행 순서가 중요한 루틴**에서만 성립한다. 순서가 없는 체크리스트에는
"다음 항목"이라는 것 자체가 없으므로 감출 것도 없다.
그래서 원칙의 문장을 이렇게 읽는다 — **"순서가 중요한 루틴에서는 한 화면에 한 항목."**
기능을 넣을지 말지 애매할 때 이 원칙으로 판단하는 것은 그대로다.

#### 뷰를 기기에 저장하지 않는다 — 여기가 제일 위험한 지점이었다

처음에는 고른 뷰를 `localStorage` 에 하나로 저장했다. **이것을 되돌렸다.**

- 출국 전 체크리스트를 목록으로 본 것이 **다음 날 아침 모닝 루틴까지 따라온다.**
  순서가 중요한 루틴에 다음 항목이 통째로 보이게 되고, 그건 이 앱이 존재하는
  이유가 조용히 무너지는 것이다. 반대 방향(모닝에서 한 항목으로 되돌린 것이
  체크리스트까지 따라오는 것)도 같이 생긴다
- **예외가 기본값으로 굳는 것**이 이 기능의 유일한 실질 위험이고, 저장이 그 통로였다
- 그래서 `start()` 마다 루틴의 `view` 로 되돌린다. 진행 상태를 저장하지 않는
  것(D-008)과 같은 방식이다. 실행 중 전환은 **그 회차에만** 걸린다
- **버린 대안**: 루틴 키별로 저장(`routine.view.<키>`). 위 문제는 안 생기지만,
  저장할 값이 늘면 D-015("이 파일이 유일한 원본")가 흐려진다. 지금은 저장하지 않는
  쪽이 규칙이 하나 적다. 매 회차 바꾸는 일이 실제로 생기면 그때 뒤집는다

#### 진행 로직은 두 뷰가 똑같은 것을 쓴다

목록 뷰는 **같은 상태를 다르게 그릴 뿐**이다. 완료·건너뛰기·이전·시간 재기·소리는
한 벌이고 뷰에 따라 갈라지지 않는다. 갈라지면 두 배로 틀린다.

- **목록에서 줄을 눌러 완료시키지 않는다.** 완료는 큰 `완료` 버튼 하나뿐이다.
  줄을 누르면 완료되게 하면 훑어보다가 손이 스치는 것만으로 항목이 넘어간다
- 지금 할 것은 목록 안에서 **채운 줄**로 뜨고, 늘 화면 가운데로 끌어온다.
  지나온 것은 걸린 시간(또는 `건너뜀`), 아직인 것은 흐리게 + 목표 시간

#### 걸린 것 하나 — 크롬에서 부드러운 스크롤이 통하지 않는다

목록 안에서 지금 할 것을 화면에 끌어오는 데 `scrollIntoView` 와
`scrollTo({behavior:'smooth'})` 둘 다 아무 일도 하지 않았다(바깥이 `overflow:hidden`).
`scrollTop` 을 직접 계산해 넣는다. 부드럽게 밀리는 맛보다 **지금 할 것이 반드시
보이는 것**이 중요하므로 바로 옮기는 쪽으로 뒀다.

#### 회귀 검사 (127건 → 149건)

메타 검사(5번)에 `view` 를 넣고, 6번을 새로 뒀다. 6번이 못박는 것은 두 가지다 —
**순서가 중요한 셋(모닝·이브닝·수련과 운동)이 `'one'` 이라는 것**과,
**뷰가 저장되지 않는다는 것**(`routine.view` 라는 글자가 본체에 없어야 한다).
목록이 순서가 중요한 루틴까지 번지는 것이 이 기능의 실패 모습이고,
검사가 잡을 수 있는 것이 정확히 거기까지다.
**목록이 실제로 읽기 편한가, 손가락으로 훑기 좋은가는 여전히 못 잡는다.**

### D-025 · 2026-08-28 · 목록 뷰는 순서와 무관하게 체크한다 — 줄마다 완료 단추

**문제**: 목록 뷰(D-024)를 만들었지만 **끝내는 방식은 여전히 순차였다.**
열네 줄이 한 화면에 보이는데 정작 완료는 위에서부터 하나씩만 되니,
5번을 먼저 챙겨도 그것을 체크할 방법이 없었다.
전체를 보여주는 이유가 "순서와 무관하게 빠르게 체킹"인데(D-024) 화면만 바뀌고
동작이 안 따라간 셈이다.

**결정**: 목록 뷰에서는 **줄마다 붙은 `완료` 단추**를 눌러 아무 것이나 끝낸다.
끝낸 줄은 **아래로 내려가 흐리게** 뜨고, 끝낸 순서대로 쌓인다.

#### 두 뷰가 갈라지는 지점은 '끝내는 방식' 하나다

| | 한 항목 뷰 | 목록 뷰 |
|---|---|---|
| 끝내기 | 큰 `완료` — 지금 것 하나 | 줄마다 `완료` — 아무 것이나 |
| 아래 단추 | `완료` · `← 이전` · `건너뛰기` | `마치기` · `↩ 되돌리기` |
| 위쪽 숫자 | `7 / 27` (지금 몇 번째) | `3 / 14 · 5:12` (몇 개 끝냈나 · 전체 시간) |
| 항목 알림(`@분`) | 울린다 | **안 울린다** — 지금 항목이 없다. 줄에 글자로만 |

기록·시간 재기·소리는 여전히 **한 벌**이다(9번 구역의 `complete()`).
갈라지는 것은 "무엇을 끝낼지 고르는 방법"뿐이다.

#### 기록을 스택에서 '끝낸 순서 목록'으로 바꿨다

예전 `state.records` 는 밀어 넣고 빼는 스택이었고, **자리 번호가 곧 항목 번호**였다 —
순서대로만 끝냈기 때문에 그래도 됐다. 목록 뷰에서는 5번을 먼저 끝낼 수 있으므로
기록마다 **항목 번호 `i` 를 들고 있어야 한다**. 그래서 `{ i, name, ms, skipped }` 다.

- `recordOf(i)` · `firstUndone()` 이 "무엇이 남았나"를 답하고, 두 뷰가 같이 쓴다
- **뷰를 바꿔도 진행이 이어진다.** 목록에서 5번만 체크하고 한 항목 뷰로 넘어가면
  `firstUndone()` 이 가리키는 1번이 뜬다. 이미 끝낸 것은 다시 나오지 않는다
- `되돌리기`(`← 이전`)는 **마지막으로 끝낸 것**을 되살린다. 두 뷰가 같은 함수다

#### `마치기` 를 큰 검은 단추로 두지 않았다

목록 뷰에는 지금 항목이 없어서 아래쪽 큰 단추가 가리킬 것이 없다.
남는 뜻은 "다 못 채우고 그만두기"뿐이라 `마치기` 로 바꾸고, **primary 를 벗겨
ghost 로 내렸다.** 진짜 조작이 줄마다 있는데 아래에 크고 검은 단추가 있으면
그것을 눌러야 할 것처럼 보이고, 잘못 누르면 루틴이 끝나 버린다.
같은 이유로 **목록 뷰에서는 `Enter`·`Space` 를 받지 않는다** — 스친 키 하나로
끝나는 일을 막는다. `←`(되돌리기)와 `v`(뷰 전환)만 남겼다.

채우지 못한 것은 요약에 **`안 함`** 으로 흐리게 남는다. 다 채우면 `마치기` 를
누를 필요 없이 저절로 끝난다.

#### 끝낸 줄의 `✓` 를 다시 누르면 되살아난다

`되돌리기` 는 마지막 하나만 되살린다. 열네 줄을 엄지로 훑다 잘못 누르는 일이
실제로 생기는데, 그때 되살릴 방법이 없으면 루틴을 다시 시작해야 한다.
그래서 끝낸 줄의 오른쪽 `✓` 가 그대로 취소 단추다.

- **버린 대안 · 줄 아무 데나 눌러도 완료** — 훑어보다 손이 스치는 것만으로
  항목이 넘어간다. 단추라는 좁은 과녁을 일부러 남겼다 (D-024 에서 이미 정한 것)

#### 흐린 쪽을 뒤집었다

D-024 에서는 **아직 안 한 것**이 흐렸다(지금 항목을 돋보이게 하려고).
이제는 반대로 **끝낸 것**이 흐리다. 목록 뷰의 주인공은 남은 일이지 한 일이 아니다.
지금 항목을 검게 칠하던 강조도 없앴다 — 순서와 무관한 목록에서 하나를 강조하면
"이것부터 하라"는 말이 되어 방금 정한 것과 어긋난다.

#### 회귀 검사 (149건 → 160건)

7번을 새로 뒀다. 줄 순서를 정하는 `listOrder(count, doneIdx)` 를 **상태를 안 쓰는
순수 함수**로 빼서 검사가 직접 돌려본다 — 아무것도 안 했을 때 · 가운데 하나 ·
끝낸 순서대로 쌓이는지 · 거꾸로 전부 · 빈 루틴 · 범위 밖 번호 · 줄 수 보존.
**여기가 틀리면 훑는 도중 줄이 엉뚱한 데로 튀어 어디까지 했는지를 잃는다.**
6번에는 줄 단추가 있는지·연결됐는지·취소가 가능한지를 덧붙였다.

**여전히 못 잡는 것**: 단추가 엄지로 눌리는 크기인가, 흐린 정도가 실제로 "끝난 것"
으로 읽히는가. `CLAUDE.md` 1번 그대로다.

### D-026 · 2026-08-28 · push 를 묻지 않는다 — 올라가지 않은 커밋은 끝나지 않은 작업이다

**문제**: 이 저장소만 Public 이라 push 를 매번 물어 왔다(2026-08-17). 그런데
실제로 돌려 보니 사용자가 **연달아 세 번 "push" 라고만 답하는** 일이 벌어졌다.
묻는 것이 판단을 돕는 게 아니라 흐름만 끊고 있었다.

**결정**: 커밋했으면 **push 까지 한다. 묻지 않는다.**
`CLAUDE.md` 7번의 "원격 업로드는 반드시 먼저 묻는다"를 뒤집는다.

- **왜 뒤집나** — 이 앱은 여러 기기에서 같은 것을 보는 것이 전제다(D-014).
  커밋만 하고 멈추면 폰과 맥앱에는 아무것도 도착하지 않는다.
  즉 **올라가지 않은 커밋은 되돌아갈 지점이 아니라 끝나지 않은 작업**이다.
  묻는 규칙은 그 마지막 한 걸음을 매번 사람 손에 떠넘기고 있었다
- **2026-08-17 의 예외가 이미 답이었다** — 그때도 "루틴 내용 갱신은 묻지 않고 바로
  push" 라는 예외를 뒀다. 근거가 "push 해야 전 기기에 반영된다"였는데,
  그 근거는 코드 변경에도 똑같이 적용된다. 예외 쪽이 규칙보다 맞았던 것이다

#### 대가로 지켜야 할 것 — 커밋 자체를 조심한다

이 저장소는 **Public 을 벗어날 수 없다.** GitHub Pages 무료 플랜이 Private 저장소를
게시하지 못하고, Private 으로 돌리면 맥앱과 안드로이드가 즉시 끊긴다.
그래서 push 는 곧 인터넷 공개이고, 커밋에 박힌 이메일도 함께 영구 공개된다.
**되돌릴 수 없다** — 지운 뒤에도 캐시와 색인에 남는다.

묻는 관문을 없앤 대신 **관문을 한 칸 앞으로 옮긴다** —
공개되면 안 되는 것을 **애초에 이 저장소에 커밋하지 않는다.**
비밀번호·토큰·개인정보가 섞일 낌새가 있으면 커밋 전에 멈추고 묻는다.

- **되돌리기·이력 삭제(`reset --hard`, `push --force`, 브랜치 삭제)는 그대로 먼저 묻는다.**
  이건 push 여부와 다른 종류의 위험이다

### D-027 · 2026-08-28 · 화면 톤은 기기 설정을 따른다 — D-023 의 `theme` 를 뒤집는다

**문제**: 톤이 루틴에 매여 있었다(D-023) — 이브닝만 어둡고 나머지는 밝다.
그래서 **기기를 어둡게 써도 아침에 앱만 하얗게 켜졌다.** 반대로 밝게 쓰는
기기에서는 저녁에만 화면이 검게 바뀌었다. 어느 쪽이든 기기의 나머지와 따로 논다.

**결정**: `theme` 에 **`'auto'`** 를 더하고 **루틴 넷 다 `'auto'` 로 바꿨다.**
맥의 시스템 설정, 안드로이드의 다크 테마를 그대로 따른다.
`'light'` · `'dark'` 는 못박는 값으로 남겨 두었지만 **지금 쓰는 곳은 없다.**

#### 이브닝의 강제 어둡게를 뺐다 — 이것이 이 결정의 진짜 내용이다

D-023 은 어두운 톤의 근거를 "잠들기 전 밝은 화면을 피하려고"라고 적었다.
그 근거 자체는 지금도 맞다. 다만 **그 일을 앱이 혼자 할 필요가 없어졌다** —
맥의 야간 모드도, 안드로이드의 다크 테마도 해질녘에 저절로 어두워진다.
앱이 따로 판단하면 기기와 어긋날 때가 생기고, 어긋난 쪽이 늘 앱이다.

⚠ **대가**: 기기를 종일 '밝게'로 두고 쓰면 **이브닝 루틴도 밝게 뜬다.**
잠들기 전 밝은 화면을 앱이 막아 주던 것이 사라진다는 뜻이다.
그게 문제가 되면 `ROUTINES.evening.theme` 을 `'dark'` 로 되돌리면 된다 —
값 하나다. 그러라고 `'light'`·`'dark'` 를 남겨 두었다.

#### 어두운 색을 두 벌 적어야 한다 — 그리고 그것이 이 변경의 유일한 위험이다

CSS 는 선택자(`body[data-theme="dark"]`)와 미디어 질의를 한 규칙으로 묶지 못한다.
그래서 같은 색을 두 번 적는다.

- **버린 대안 · `light-dark()` CSS 함수** — 한 벌로 끝나지만 비교적 새 문법이라
  옛 안드로이드 웹뷰에서 통째로 무시될 수 있다. 이 앱은 **어디서 열어도 동작하는
  것**이 원칙이라(D-002) 확실한 쪽을 골랐다
- **버린 대안 · JS 로 `data-theme` 을 계산해 넣기** — 두 벌은 없어지지만,
  스크립트가 돌기 전 첫 화면이 잘못된 색으로 한 번 번쩍인다
- 그래서 **회귀 검사 8번이 두 벌을 값 그대로 비교한다.** 일부러 한 글자를
  어긋나게 해 검사가 실패하는 것까지 확인했다

#### 위쪽 띠 색만은 CSS 가 못 정한다

홈 화면에 추가한 앱의 위쪽 띠는 `meta[name="theme-color"]` 로 정해진다.
그래서 JS 가 지금 톤을 계산해(`resolvedTheme()`) 넣어 주고,
**루틴 도중 기기 설정이 바뀌면**(해질녘 자동 전환) 그때도 다시 맞춘다.

여기서 **CSS 와 JS 가 같은 질의를 봐야 한다.** 뒤집어 보는 실험에서 한쪽만 바꿨더니
화면은 밝은데 띠만 어두운 상태가 실제로 나왔다. 검사 8번이 그것도 함께 본다.

### D-028 · 2026-09-03 · 시작 화면(스플래시) 아이콘은 여백을 가진 것으로 따로 준다

크림색 바탕을 주황 정사각형이 모서리까지 꽉 채워, 로고 하나가 화면을 덮은 것처럼 보였다.

**원인**: D-019 에서 "PWA 는 OS 가 마스크로 잘라내므로 꽉 채워야 한다"고 정했는데,
그 말이 맞는 자리는 **홈 화면 아이콘**뿐이다. **시작 화면은 아이콘을 자르지 않고 준 대로
그린다.** 맥 독에서 겪은 것(D-019)과 같은 문제를, 자리만 바꿔 다시 겪은 것이다.

**결정**: 웹 아이콘을 용도로 나눈다. `tools/make-icons.py` 가 다섯 개를 만든다.

| 용도 | 파일 | 모양 |
|---|---|---|
| 파비콘 · iOS 홈 화면 · 안드로이드 홈 화면(`maskable`) | `icon-192.png`, `icon-512.png` | 꽉 채움 (그대로) |
| **안드로이드 시작 화면**(매니페스트 `any`) | `icon-inset-192.png`, `icon-inset-512.png` | 824/1024 둥근 사각형 + 투명 여백 |
| 맥 독 | `mac/icon-mac-1024.png` | 같은 여백 도형 (그대로) |

크롬은 홈 화면 아이콘에 `maskable` 을, 시작 화면에 `any` 를 쓴다. 매니페스트에 둘을
따로 적어 두면 각 자리가 알아서 맞는 것을 집어간다.

**여백 비율**: 맥과 같은 **824/1024(=80.5%)**, 모서리 반경은 그 크기의 22.4%.
같은 문제였으니 이미 검증된 같은 값을 쓴다. 기존 세 파일은 **바이트까지 그대로다** —
맥 아이콘을 그리던 함수를 이름만 `inset_icon` 으로 바꿔 웹에도 같이 쓴 것이다.

**버린 대안**: `icon-192.png` 자체에 여백을 넣기. 한 파일로 끝나지만 홈 화면에서
**여백이 두 번 들어가** 아이콘이 쪼그라든다 — D-019 가 이미 밝힌 함정이다.

**한계**: iOS 는 `apple-touch-icon`(꽉 채운 쪽)을 쓰고 시작 화면에 로고를 띄우지 않으므로
이 변경의 영향을 받지 않는다. **안드로이드 실기에서 아직 눈으로 확인하지 않았다** —
이미 설치된 앱은 **지우고 다시 설치해야** 새 아이콘이 반영된다.

### D-029 · 2026-09-03 · 아이콘 주소에 지문을 찍어 저절로 갈아끼우게 한다

**문제**: 아이콘을 고쳐 올려도 기기에 반영되지 않아, **매번 지우고 다시 설치**해야 했다.

**원인**: 크롬은 설치된 앱의 매니페스트를 하루에 한 번쯤 다시 읽고 달라졌으면 저절로
갈아끼운다. 그런데 이 프로젝트는 **파일 이름을 그대로 두고 그림만 바꾼다.**
주소가 같으면 크롬이 "안 바뀌었다"고 보고 넘어갈 수 있다.

**결정**: `tools/make-icons.py` 가 아이콘을 만든 뒤 **파일 내용의 지문(sha256 앞 8자리)을
매니페스트의 `src` 에 `?v=` 로 찍는다.** 그림이 바뀌면 주소가 반드시 바뀌고, 그림이
그대로면 지문도 그대로라 쓸데없는 갱신은 일어나지 않는다. 사람이 기억할 일이 없다 —
아이콘을 만드는 도구가 곧 주소를 고치는 도구다.

**곁따라온 것 둘**

- **서비스워커가 아이콘 이름을 더는 적지 않는다.** 매니페스트를 읽어 그 `src` 를 그대로
  쓴다. 두 곳에 적어 두면 지문이 붙는 순간 한쪽이 낡고, 그 어긋남은 **오프라인에서만**
  드러나 알아채기 어렵다
- **회귀 검사 9번**을 뒀다. 매니페스트가 올바른 JSON 인가, 모든 아이콘에 지문이 있는가,
  **그 지문이 실제 파일과 맞는가**, `any` 와 `maskable` 이 다 있는가, 서비스워커가
  아이콘 이름을 다시 적지 않았는가. 지문이 어긋난 채 올라가면 기기에서는 옛 아이콘이
  계속 뜨는데 여기서는 아무 일도 없어 보인다 — 그 침묵을 막는 것이 이 검사다

**한계**: **즉시가 아니다.** 크롬은 앱을 켤 때 하루에 한 번꼴로만 확인하고, 확인한 뒤에도
새 앱 꾸러미를 받아 까는 데 시간이 걸린다. **하루 안팎**으로 보면 된다. 급하면 지우고
다시 설치하는 길은 그대로 있다. iOS 는 홈 화면에 추가한 아이콘을 아예 갱신하지 않는다.

### D-030 · 2026-09-03 · 잘릴 것을 미리 빼고 그린다 — 시작 화면 로고의 진짜 원인

**문제**: D-028 로 여백 있는 아이콘을 따로 줬는데도 **시작 화면 로고는 그대로 컸다.**

**원인**: 두 가지를 잘못 짚었다.

1. **그 화면은 `any` 아이콘을 안 쓴다.** 스크린샷의 로고는 **스퀘어클** 이었다 —
   안드로이드가 홈 화면 아이콘(`maskable`)을 마스크로 잘라 그린 모양이다.
   D-028 이 손댄 `any` 아이콘은 이 자리에 나오지 않는다
2. **주황 타일 크기는 우리가 못 정한다.** 스크린샷에서 재 보니 **237dp** 였고,
   이는 안드로이드 12+ 시작 화면의 **고정 규격 240dp** 다. 앱이 바꿀 수 없다

**정말로 큰 것은 타일이 아니라 그 안의 체크였다**. 적응형 아이콘은 가운데 72/108
(=66.7%)만 남기고 **1.5배로 확대해** 자른다. 캔버스 기준 49% 로 그린 체크가 화면에서는
타일의 **74%** 가 된다 — 안드로이드 권장(240dp 안의 160dp = 67%)을 넘는 값이다.

**결정**: 꽉 채운 아이콘의 체크를 **미리 72/108 만큼 줄여** 그린다. 마스크를 거치고 나면
**48%** 로, 여백 있는 아이콘(맥·`any`)의 체크와 같은 비율이 된다. 어느 자리에서 봐도
같은 크기로 보인다는 뜻이다.

**왜 이 값인가**: 고른 값이 아니라 **되돌리는 값**이다. OS 가 1.5배 키우니 1/1.5 로
줄인다. "여백을 주면 두 번 줄어든다"(D-019)의 정확한 반대편이다.

**D-028 을 버리지 않는다**: 여백 있는 `any` 아이콘은 설치 대화상자·작업 전환기처럼
**자르지 않고 그리는 자리**에서 여전히 맞다. 다만 **시작 화면의 원인은 그쪽이 아니었다** —
D-028 은 맞는 고침이었으나 **다른 자리를 고친 것**이었다.

**한계**: 안드로이드 실기에서 아직 못 봤다. 마스크를 흉내 내어 그려 보니 **전 그림이
스크린샷과 일치**했고 후 그림에서 체크가 48% 로 줄었다 — 흉내가 맞다는 근거는 되지만
실기 확인은 아니다. **이 저장소 밖의 기기 화면이 유일한 판정 수단이다.**
