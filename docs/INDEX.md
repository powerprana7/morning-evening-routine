# 문서 지도 (INDEX)

문서마다 **답하는 질문이 하나씩** 있다. 같은 내용을 두 군데 적지 않기 위한 구분이다.
새 문서를 만들기 전에, 기존 문서 중 그 질문을 맡을 곳이 없는지 먼저 본다.

## 읽는 순서

1. `docs/STATUS.md` — **지금 어디까지 왔나** (세션 시작 시 이것만 읽으면 된다)
2. `CLAUDE.md` — **어떻게 일하나** (지켜야 할 규칙)
3. 필요할 때 아래에서 골라 본다

## 질문별

| 이 질문이 생기면 | 이 문서를 본다 | 갱신 시점 |
|---|---|---|
| 지금 뭐가 되고 뭐가 안 되나? 다음에 뭘 하지? | `docs/STATUS.md` | 동작이 바뀌는 커밋마다 |
| **언제 무엇이 바뀌었나?** 지난 갱신에서 뭘 했나? | `docs/UPDATES.md` | 버전(날짜)이 올라갈 때마다 |
| 어떻게 일해야 하나? | `CLAUDE.md` | 일하는 방식이 바뀔 때 |
| 이 화면/기능이 **어떻게 동작해야** 하나? | `docs/SPEC.md` | 동작을 새로 정하거나 바꿀 때 |
| 왜 이렇게 만들었나? 왜 그 대안을 버렸나? | `docs/DECISIONS.md` (D-001~) | 핵심 규칙·구조를 바꿀 때 |
| 다음에 할 일 목록은? | `docs/BACKLOG.md` (B-01~) | 작업을 시작·완료할 때 |

**STATUS 와 UPDATES 의 경계**: STATUS 는 *지금 어떤가*(현재 시점 하나뿐, 지난 상태를
덮어쓴다), UPDATES 는 *언제 무엇이 바뀌었나*(쌓기만 하고 지우지 않는다). STATUS 만
있으면 "지난주에 뭘 바꿨지"를 `git log` 로 뒤져야 하는데, 그건 `CLAUDE.md` 9번이
하지 말라고 못박은 방법이다 (D-023).

**UPDATES 와 DECISIONS 의 경계**: UPDATES 는 *바뀐 것*, DECISIONS 는 *바꾼 이유*.
UPDATES 의 각 칸은 결정 번호를 가리키기만 하고 근거를 옮겨 적지 않는다.

**SPEC 과 DECISIONS 의 경계**: SPEC 은 *무엇이 어떻게 동작하는가*(현재형 규격),
DECISIONS 는 *왜 그렇게 정했고 무엇을 버렸는가*(과거형 이력). 규격이 바뀌면 SPEC 을
고쳐 쓰고, 바꾼 이유는 DECISIONS 에 새 번호로 **덧붙인다**.
